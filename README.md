# CareSignal

A discharge-planning AI agent for hospital care teams. It finds patients at high risk of
30-day readmission, explains what is driving the risk, checks their medication list for
interactions, and answers questions about the cohort in plain language.

> **Synthetic data only.** Every patient is generated by a seeded random process. This is a
> working reference application, not a certified medical device; see [Before real use](#before-real-use).

## How it fits together

```
 React + TypeScript UI  ──►  FastAPI  ──►  Claude agent (tool loop)
        (web/)               (api.py)          (agent.py)
                                │                  │  MCP (stdio)
                                │                  ▼
                                └──────►  MCP server (mcp_server.py)
                                          6 clinical tools over service.py
                                                   │
                         pandas cohort  +  PyTorch risk model (model.py)
                                                   │
                              R validation (r/analysis.R)   AWS CDK (infra/)
```

| Piece | Tech | Where |
| --- | --- | --- |
| Synthetic cohort, feature pipeline | NumPy, pandas | `caresignal/data.py`, `caresignal/model.py` |
| Readmission risk model + per-patient drivers | PyTorch | `caresignal/model.py` |
| Clinical tools (patients, risk, interactions, cohort stats) | MCP server | `caresignal/mcp_server.py` |
| Agent | Claude (`claude-opus-5-5`) via the Anthropic SDK tool runner, as an MCP client; Amazon Bedrock and Google Gemini are switchable providers | `caresignal/agent.py` |
| REST API | FastAPI | `caresignal/api.py` |
| Web app | TypeScript, React, Vite | `web/` |
| Independent model validation | R (base only) | `r/analysis.R` |
| Deployment | Google Cloud Run + Gemini (`deploy/gcp/`), or AWS CDK (TypeScript): Fargate + ALB + Bedrock (`infra/`) | `Dockerfile` |

The agent holds no clinical logic of its own: every fact it states comes from an MCP tool
call. The same server therefore works unchanged in Claude Desktop or Claude Code:

```json
{ "mcpServers": { "caresignal": { "command": "python", "args": ["-m", "caresignal.mcp_server"], "cwd": "/path/to/caresignal" } } }
```

## Run it

```bash
pip install -r requirements-dev.txt
```

```bash
python -m caresignal.model        # generate cohort + train (about 10 s on CPU) -> artifacts/
```

```bash
npm --prefix web install && npm --prefix web run build
```

```bash
export ANTHROPIC_API_KEY=...      # needed only for the chat panel
uvicorn caresignal.api:app --port 8000
```

To use Google Gemini instead (it has a free tier; create a key in Google AI Studio):

```bash
export CARESIGNAL_PROVIDER=gemini GEMINI_API_KEY=...
uvicorn caresignal.api:app --port 8000
```

The Gemini path uses Google's OpenAI-compatible endpoint and defaults to
`gemini-3.5-flash-lite` (override with `CARESIGNAL_GEMINI_MODEL`). Free-tier Gemini is rate
limited and its larger models are sometimes unavailable under load. Check Google's
free-tier data terms before sending anything other than synthetic data.

Open http://localhost:8000. Without an API key the patient list, risk drivers and
medication checks all work; the chat panel reports that the LLM is not configured.

Other entry points:

```bash
python -m caresignal.agent        # terminal chat with the agent
```

```bash
Rscript r/analysis.R              # writes artifacts/r_validation.md
```

```bash
pytest                            # model, service, MCP-over-stdio, REST API, agent loop
```

For UI development run `npm --prefix web run dev` (proxies `/api` to port 8000).

## The model (synthetic demo)

A small MLP trained on 17 features (age, prior admissions, length of stay, Charlson index,
labs, comorbidities, living situation, discharge disposition). On the held-out test split
of the default cohort (6,000 patients, 18% readmitted):

- AUROC **0.76**, Brier score 0.127
- The R script fits a plain logistic regression on the same split and scores **0.77**. The
  neural net does not beat the simple baseline on this data; it is here to show the
  PyTorch serving path, and the R report makes that comparison visible on every run.

"Drivers" are occlusion attributions: how many points the predicted risk moves when one
feature is replaced by the cohort average.

## Real data

CareSignal runs on three data sources, chosen with `CARESIGNAL_SOURCE`:

| Source | What it is | Setup |
| --- | --- | --- |
| `synthetic` (default) | Generated demo cohort | none |
| `uci` | **Real** de-identified inpatient encounters: 101,766 diabetes admissions from 130 US hospitals, 1999–2008 (UCI Machine Learning Repository, Strack et al. 2014) | `python -m caresignal.model --dataset uci` (downloads once, about 40 s to train) |
| `fhir` | **Live** hospital record system over FHIR R4, refreshed every `CARESIGNAL_FHIR_TTL` seconds (default 900) | set `CARESIGNAL_FHIR_BASE` (and `CARESIGNAL_FHIR_TOKEN`) |

Results on real data (held-out patients, 15,001 encounters, 11.4% readmitted within 30 days):

- PyTorch model: **AUROC 0.65**, Brier 0.100. The R logistic regression on the same split scores 0.64
  (`artifacts/uci/r_validation.md` after `Rscript r/analysis.R artifacts/uci`).
- The synthetic demo scores 0.76 because it was generated from a known formula. Real readmission is harder
  to predict, and 0.65 is the honest figure to quote.

**How the real data maps onto the model** (`caresignal/uci.py`, `caresignal/fhir.py`):

| Model input | UCI dataset | Live FHIR |
| --- | --- | --- |
| Age | decade bracket, midpoint used (25 means 20–29) | `Patient.birthDate` |
| Length of stay | `time_in_hospital` (days) | Encounter period |
| Prior admissions (12 months) | `number_inpatient` | finished inpatient encounters in the prior 365 days |
| Medications / diagnoses | counts from the record | active `MedicationRequest` count / `Condition` count |
| HbA1c | three categories (Norm, >7, >8) mapped to 5.5 / 7.5 / 9.0 | latest LOINC 4548-4 |
| Heart failure, COPD, diabetes, CKD | ICD-9 codes | ICD-10 codes (I50, J43/J44, E08–E13, N18) |
| Discharged to SNF / home health | discharge id 3 / 6 | UB-04 codes 03 / 06 |
| 30-day readmission (label) | `readmitted` = `<30` | next admission within 30 days; unknown if none on record |

Not recorded by either source (shown as "not recorded" in the app): creatinine, blood pressure, BMI,
living situation, and Charlson index. Encounters ending in death or hospice are excluded. In the UCI
data, patients are split whole into train, validation and test, so no patient appears in two splits.

**Before any identifiable patient data goes in**, these are required and are not yet done:

1. **Access control.** The app has no login. Cloud Run is private by default, so it sits behind Google
   sign-in; identity-aware access (IAP, with per-user rules) is the next step.
2. **A data agreement covering every vendor in the path.** The Gemini free tier is not covered for
   identifiable data. The app refuses to start with `CARESIGNAL_SOURCE=fhir` and `CARESIGNAL_PROVIDER=gemini`
   unless `CARESIGNAL_ALLOW_FREE_TIER_LLM=1` is set, which is only for non-identifiable test data. Use
   Bedrock or an Anthropic key under a BAA. The cloud project needs a BAA too.
3. **Audit logging** is in place: every patient-record view and agent question is written as one JSON
   line to Cloud Logging (question text is not logged). Retention and review are still to be set up.
4. **A licensed drug-interaction database.** `service.py` holds only illustrative pairs.
5. **Clinical validation** on your own patients, including calibration by site and subgroup fairness,
   and whatever regulatory review applies.

Connecting a real hospital means its IT team issues a FHIR endpoint and a SMART access token. Store the
token in Secret Manager (`FHIR_TOKEN_SECRET=<secret name>` on the deploy script), never in the repository.

## Deploy to Google Cloud (Cloud Run + Gemini)

```bash
PROJECT_ID=your-project-id ./deploy/gcp/deploy.sh
```

Run it from the repository root in Cloud Shell (or anywhere `gcloud` is logged in). It
builds the Dockerfile with Cloud Build and deploys one Cloud Run service that serves the
UI, API, agent and MCP server. The script asks for your Gemini API key once and stores it
in Secret Manager; the service reads it from there with a dedicated service account.

The app has no login of its own, so the service is **private by default**. View it with
`gcloud run services proxy caresignal --region us-central1 --port 8080`, or pass
`PUBLIC=1` to the script to open the URL to anyone. Scales to zero when idle; the first
request after idle takes several seconds while the model loads.

If the chat reports invalid credentials after deploying, replace the stored key with
`./deploy/gcp/set-key.sh`; it tests the key against Gemini before saving it.

## Deploy to AWS

```bash
cd infra && npm install && npx cdk bootstrap && npx cdk deploy
```

This builds the Docker image and runs it on ECS Fargate in private subnets behind a public
Application Load Balancer. The container sets `CARESIGNAL_PROVIDER=bedrock`, so the agent
calls Claude through Amazon Bedrock using the task's IAM role (no API key to store). Your
account needs Bedrock model access for the Claude model in that region. `npx cdk destroy`
removes everything.

## Before real use

This repository deliberately stops short of things a deployment touching real patient
data must have:

- **Authentication and authorisation.** The API has none; the stack's load balancer is
  public HTTP. Add TLS, SSO and role-based access before exposing it.
- **Audit logging** of who viewed which patient and what the agent was asked.
- **A real data source** (EHR/FHIR) in place of the synthetic cohort, under a BAA with
  every vendor in the path (cloud and LLM provider).
- **A licensed drug-interaction database.** `service.py` holds a dozen illustrative pairs.
- **Clinical validation** of the model on the target population, with calibration and
  subgroup-fairness review, plus whatever regulatory review applies.
